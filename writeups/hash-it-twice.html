Hash It Twice

How HMAC turns a plain hash into a tamper seal, and why the obvious shortcut gets forged.

~12 min read · beginner-friendly · interactive

The short version

If you and a server share a secret key, HMAC lets the server prove a message came from someone with that key and wasn't changed on the way. The simple approach, hashing the key and message together, can be forged without knowing the key. HMAC avoids that by hashing twice. When you check a tag, use a constant-time comparison, not ==.

Three ideas you need first

If you already know what a hash function, hex and XOR are, skip ahead.

What's a hash function?

A hash function turns any input into a short, fixed-size fingerprint. SHA-256 always gives back 32 bytes, whether you feed it one letter or a whole movie. Three properties matter here:

  • Same input, same output. Hash "hello" twice and you get the same fingerprint both times.
  • Tiny change, totally different output. "hello" and "hellp" have fingerprints that look completely unrelated.
  • One-way. Given a fingerprint, you can't work backwards to the input.

On its own, a hash proves nothing about who sent something. Anyone can hash anything. That's the gap HMAC fills.

What do 0x36 and f7bc83… mean?

Computers store data as bytes, and a byte is a number from 0 to 255. Writing bytes in hexadecimal (base 16, digits 0–9 then a–f) means every byte is exactly two characters: 00 is 0, 36 is 54, ff is 255. The 0x prefix just says "this is hex". A 32-byte SHA-256 output is 64 hex characters.

What's XOR (⊕)?

XOR compares two values bit by bit. Each output bit is 1 if the input bits are different and 0 if they're the same:

  0110 1011   (a key byte)
⊕ 0011 0110   (0x36)
= 0101 1101

Two things make XOR useful here. XOR-ing with the same value twice gets you back where you started. And XOR-ing a key with two different constants gives you two different-looking keys from one secret.

The problem HMAC solves

HMAC is in a lot of places: GitHub webhook signatures, HS256 JWTs, AWS request signing, the six-digit codes in an authenticator app, and the key schedule of TLS 1.3.

Think of a wax seal pressed with a ring that only you and the receiver own. Anyone can read the letter. But if the seal is intact and matches the ring, the receiver knows two things: nobody changed the letter, and it came from someone with the ring.

HMAC is that seal for data. Two parties share a secret key. The sender computes a short tag from the key and the message and sends both. The receiver recomputes the tag with their copy of the key and checks that it matches. This isn't encryption: the message stays readable. It only proves the message is authentic and unchanged.

The obvious recipe, and how it breaks

The first idea most people have is to glue the key in front of the message and hash the result: tag = SHA256(key ‖ message), where ‖ means "followed by". Without the key, you can't produce the right fingerprint. Right?

Not quite. The weakness is in how SHA-256 works inside:

  1. It pads the input and cuts it into 64-byte blocks.
  2. It starts from a fixed 32-byte state and mixes in one block at a time, updating the state after each.
  3. When the blocks run out, the final state is the hash.

So anyone holding a tag can load it back into SHA-256 as the starting state and keep feeding in more data. The result is a valid tag for key ‖ message ‖ padding ‖ anything, made without the key. This is called a length extension attack. The attacker does need to know how long the key is to get the padding right, but they can usually just try every likely length. How HMAC fixes it

HMAC (Bellare, Canetti and Krawczyk, 1996; RFC 2104) hashes twice, with two keys derived from your one key:

HMAC(K, m) = H( (K′ ⊕ opad) ‖ H( (K′ ⊕ ipad) ‖ m ) )
H
the hash function, here SHA-256
K′
your key, stretched to exactly 64 bytes
m
the message
⊕
XOR, byte by byte
‖
"followed by" (concatenation)
ipad / opad
the bytes 0x36 / 0x5C, repeated 64 times

Read it from the inside out:

  1. Stretch the key. Pad it with zero bytes to 64 bytes, one SHA-256 block. If it's longer than 64 bytes, hash it first, then pad.
  2. Make two keys. XOR the stretched key with ipad to get the inner key, and with opad to get the outer key. The two constants differ in exactly half their bits, so the two keys look unrelated to the hash.
  3. Inner hash. Hash the inner key followed by the message. You get 32 bytes.
  4. Outer hash. Hash the outer key followed by those 32 bytes. That's the tag.

Why the second hash saves it

An attacker can still try length extension on an HMAC tag, but they're only extending the outer hash. That gives them a hash of outer key ‖ inner hash ‖ padding ‖ extra. The verifier never computes anything with that shape. A real tag is always the outer key followed by exactly 32 bytes, and those 32 bytes are a fresh inner hash of the new message. Producing that inner hash requires the key.

The same structure is why HMAC-MD5 and HMAC-SHA1 still have no practical forgeries, even though MD5 and SHA-1 collisions are cheap to find. For new code, use SHA-256 anyway.

Length extension, live

A toy server holds a random 16-byte secret and signs a query string two ways: the naive SHA256(secret ‖ msg) and real HMAC-SHA256. You get the message and both tags. You don't get the secret, only its length, and attackers can usually just try every length. Then you forge.

  1. The server signs user=noam&role=guest and hands you the tags.
  2. You load the naive tag back into SHA-256 as if you'd hashed the message yourself.
  3. You keep hashing &role=admin and get a new tag. The secret never appears.
  4. Press the button and see which server believes you.

Checking tags safely

The last trap is on the receiving end. Picture a combination lock that clicks each time you get a digit right. You wouldn't need to try every combination: you'd find the first digit, then the second, and so on.

Comparing tags with == is that lock. The comparison stops at the first byte that differs, so a guess with more correct leading bytes takes slightly longer to reject. By measuring response times, an attacker can recover a valid tag one byte at a time.

The fix is a comparison that always checks every byte, no matter where the first difference is: Python's hmac.compare_digest, Node's crypto.timingSafeEqual, or Go's hmac.Equal.

The whole thing, by hand

HMAC from scratch in Python, checked against the standard library. In real code, call hmac.new instead.

import hashlib, hmac

def my_hmac(key: bytes, msg: bytes, H=hashlib.sha256) -> bytes:
    B = H().block_size                       # 64 bytes for SHA-256
    if len(key) > B:
        key = H(key).digest()                # long keys get hashed first
    key = key.ljust(B, b"\x00")              # then zero-padded to one block

    k_in  = bytes(b ^ 0x36 for b in key)    # ipad
    k_out = bytes(b ^ 0x5C for b in key)    # opad

    inner = H(k_in + msg).digest()
    return H(k_out + inner).digest()


key = b"key"
msg = b"The quick brown fox jumps over the lazy dog"
tag = my_hmac(key, msg)
assert tag == hmac.new(key, msg, hashlib.sha256).digest()
print(tag.hex())  # f7bc83f430538424b13298e6aa6fb143ef4d59a14946175997479dbc2d1a3cd8

# verifying: never ==
def verify(key, msg, received_tag) -> bool:
    return hmac.compare_digest(my_hmac(key, msg), received_tag)

Using it in real code

  • Use a random key at least as long as the hash output: 32 bytes for SHA-256. Longer than 64 bytes adds nothing, because it gets hashed down to 32.
  • Sign a timestamp or nonce along with the data, or someone can replay an old, valid message.
  • Verify the exact bytes that were signed, not a re-serialized copy that might differ in spacing or field order.
  • Need verify-only parties? Use real signatures like Ed25519 instead. With HMAC, anyone who can check a tag can also make one.

Recap

  • A hash alone proves nothing about who sent a message. A MAC adds a shared secret key.
  • SHA256(key ‖ message) is broken: the tag is SHA-256's internal state, so attackers can keep hashing from it.
  • HMAC hashes twice, with an inner key and an outer key made from your key with 0x36 and 0x5C.
  • Extending an HMAC tag only extends the outer hash, which the verifier never accepts.
  • Always compare tags in constant time.

HMAC is Mihir Bellare, Ran Canetti and Hugo Krawczyk's construction (CRYPTO 1996), standardized as RFC 2104 and FIPS 198-1. The worked example matches the well-known HMAC-SHA256 test value.
